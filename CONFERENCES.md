# Совещания по LAN: запуск на другом компьютере

## Что работает

Главная страница `/` использует FastAPI и PostgreSQL: создание и планирование встреч, приглашения, аудио/видео WebRTC, демонстрация экрана, чат, запись, расшифровка с именами участников, промежуточный анализ, поручения с исполнителем/сроком/цитатой, итоговый протокол, PDF/DOCX и WAV. Изменения поручений сохраняются на сервере. Напоминания показываются в приложении; браузерные уведомления работают при открытом сайте и выданном разрешении.

Начальные списки пустые. Приложение не создаёт примерные встречи, участников, реплики или поручения. Для ИИ-результатов нужны доступные Whisper и Ollama.

## 1. Настроить сервер приложения

На компьютере, где будет Docker Desktop / Docker Engine с Compose v2, откройте корень проекта:

```sh
cp .env.conference.example .env
```

В PowerShell вместо `cp` можно использовать `Copy-Item`. В `.env` обязательно замените:

```dotenv
SITE_HOST=192.168.1.100
OLLAMA_URL=http://192.168.1.101:11434
OLLAMA_MODEL=qwen3:8b
```

- `SITE_HOST` — LAN IPv4 компьютера **с приложением**, без протокола и порта. Желательно закрепить адрес в роутере.
- `OLLAMA_URL` — адрес **вашего другого ПК с Ollama**. Контейнер Ollama на сервере приложения не запускается.
- `OLLAMA_MODEL` — точное имя установленной текстовой модели.
- `POSTGRES_PASSWORD` — пароль новой базы. Для существующего Docker-тома используйте прежний пароль: изменение переменной не меняет пароль уже созданной базы.
- `CONFERENCE_ACCESS_KEY` — необязательный общий ключ для создания встреч. Приглашённым он не нужен.

Если раньше запускали стек с `backend/.env`, перенесите его значения подключения и пароль базы в новый `.env`. Не удаляйте тома ради обновления. Миграции выполняются автоматически.

## 2. Ollama на другом ПК

Установите модель на том ПК:

```sh
ollama pull qwen3:8b
```

Настройте переменную окружения процесса Ollama `OLLAMA_HOST=0.0.0.0:11434` и перезапустите Ollama. Разрешите вход на TCP 11434 только из вашей доверенной LAN. `OLLAMA_ORIGINS` для этого приложения не нужен: запросы идут с backend, не из браузера. Проверка с сервера приложения:

```sh
curl http://192.168.1.101:11434/api/tags
```

Ollama обрабатывает **текст**. Для распознавания голоса дополнительно нужен сервис Whisper. Выберите один из вариантов ниже.

## 3A. Whisper на сервере приложения (самый простой запуск)

Оставьте `SPEECH_URL=http://speech:8001` и выполните:

```sh
docker compose --profile speech up -d --build
```

При первом запуске скачиваются публичные веса `Systran/faster-whisper-large-v3`, затем модель работает локально. Hugging Face здесь — источник весов; токен HF для этого сценария не требуется. Аудио туда не отправляется. CPU-режим может обрабатывать звук медленнее разговора: для анализа без нарастающей очереди предпочтителен отдельный ASR-сервер с GPU.

## 3B. Whisper на другом ПК, рядом с Ollama

Скопируйте проект на ПК с моделями. Создайте там `.env` из примера, задайте непустой `SPEECH_API_KEY` и запустите:

```sh
docker compose -f compose.speech.yml up -d --build
```

Для NVIDIA GPU нужны подходящий драйвер и NVIDIA Container Toolkit:

```sh
docker compose -f compose.speech.yml -f compose.speech.gpu.yml up -d --build
```

На сервере **приложения** укажите тот же ключ и адрес ASR:

```dotenv
SPEECH_URL=http://192.168.1.101:8001
SPEECH_API_KEY=ваш-общий-секрет
```

Запустите приложение без профиля speech:

```sh
docker compose up -d --build
```

Разрешите TCP 8001 на ПК с Whisper только для сервера приложения. Whisper и Ollama используют ресурсы совместно; скорость и подходящая модель зависят от RAM/VRAM. В частности, большие модели на CPU не гарантируют realtime.

## 4. HTTPS для всех участников

В браузере другого ПК камера и микрофон требуют защищённого контекста. Стек содержит Caddy с локальным центром сертификации. После запуска скопируйте его **публичный корневой сертификат**:

```sh
docker compose cp gateway:/data/caddy/pki/authorities/local/root.crt ./conference-root.crt
```

Передайте этот сертификат каждому участнику и установите его как доверенный корневой сертификат на каждом тестовом компьютере:

- **Windows:** импорт в «Доверенные корневые центры сертификации» текущего пользователя через `certmgr.msc`.
- **macOS:** импорт в «Связку ключей», затем для этого сертификата «Доверие → Всегда доверять».
- **Linux:** добавьте сертификат в доверенные центры ОС/браузера согласно вашему дистрибутиву.

После импорта перезапустите браузер. Если используется отдельное хранилище доверия Firefox, импортируйте сертификат и туда. Доверяйте только сертификату своего сервера; приватные ключи из Docker-тома не передавайте. Простого обхода предупреждения HTTPS может быть недостаточно для доступа к микрофону.

Открывайте **одинаковый адрес** на сервере и у коллег:

```text
https://192.168.1.100:8443
```

Разрешите TCP 8443 на сервере. Для WebRTC участники должны иметь прямую сетевую связность: гостевой Wi-Fi с изоляцией клиентов и блокировка UDP могут мешать. Публичные STUN/TURN не используются. В маршрутизируемых/изолированных сетях настройте свой TURN и передайте JSON-массив `RTC_ICE_SERVERS` в `.env`.

`http://localhost:5173` доступен только на сервере для локальной проверки. Не отправляйте коллегам приглашения, созданные с адресом localhost. Токены участника привязаны к хранилищу браузера и origin; переход на другой адрес открывает другое хранилище.

Основание: [защищённый контекст getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [локальные сертификаты Caddy](https://caddyserver.com/docs/automatic-https#local-https).

## 5. Проверка двумя компьютерами

1. На обоих откройте LAN HTTPS-адрес без предупреждения о сертификате. Используйте наушники, чтобы избежать эха.
2. Организатор: «Новая конференция», имя, тема, согласие → создать → войти в звонок, разрешить микрофон.
3. Скопируйте приглашение и откройте его на другом ПК. Участник вводит своё имя, подтверждает согласие и входит в звонок. Проверьте звук в обе стороны, камеру, чат и демонстрацию экрана.
4. В комнате проверьте диагностику: обработчик, Whisper и Ollama должны быть доступны. Организатор включает запись; у всех появляется индикатор.
5. Произнесите несколько фраз по-русски и по-казахски, затем поручение с именем коллеги и конкретной датой. Аудио отправляется порциями примерно по 8 секунд; расшифровка появляется после обработки каждой порции. Анализ запускается с интервалом от 30 секунд плюс время вывода модели.
6. Проверьте вкладки расшифровки и поручений на обоих ПК. Измените исполнителя/срок и убедитесь, что правка видна другому участнику.
7. Остановите запись или завершите встречу. Дождитесь отправки последних фрагментов, обработки очереди и итогового анализа. Скачайте PDF, DOCX и WAV. Пока запись/обработка не завершена или есть ошибки, экспорт протокола блокируется.
8. Проверьте сохранение встречи после обновления страницы и напоминания о поручениях. При временном сбое отправки оставьте страницу открытой: фрагменты сохраняются в IndexedDB и повторно отправляются; после закрытия браузера очередь продолжится при повторном открытии этой комнаты с тем же профилем.

## Диагностика

```sh
docker compose ps
docker compose logs --tail=100 api live-worker gateway
# Для Whisper на этом сервере:
docker compose --profile speech logs --tail=100 speech speech-bootstrap
# Для отдельного ПК с Whisper:
docker compose -f compose.speech.yml logs --tail=100 speech bootstrap
```

В комнате есть проверка ИИ-сервисов и повтор обработки неудачных фрагментов. Если голос собеседника не слышен, проверьте разрешение микрофона, выбранное устройство, воспроизведение звука браузером и сетевую связность участников. Закрытие вкладки организатора не завершает общую встречу: для этого используйте «Завершить».

Остановка с сохранением данных: `docker compose down`. Не добавляйте `-v`, если хотите сохранить встречи и сертификаты.

## Архитектура и границы

- React → HTTPS/Caddy → FastAPI; PostgreSQL хранит комнаты, участников, сообщения, реплики и поручения. Записи хранятся в Docker-томе.
- WebRTC mesh: каждый участник соединяется с остальными напрямую. Начальный лимит — 8 одновременных участников. Это LAN-конференции, а не SFU для сотен пользователей.
- Запускайте **один API-процесс и один live-worker**: сигналинг/присутствие находятся в памяти API. После перезапуска браузеры переподключаются; комнаты и очередь сохранены в БД.
- Каждый участник отправляет только свой микрофон. Реплики привязываются к введённому имени через отдельный аудиопоток. Это не биометрическое распознавание личности. Если за одним микрофоном говорят несколько человек, они будут подписаны одним именем. Речь из системного звука демонстрируемого экрана не записывается.
- Whisper multilingual поддерживает RU/KK; качество смешанной речи требует проверки на реальных записях и вашем оборудовании. Модель может ошибаться, поэтому проверяйте поручения по цитатам и редактируйте результат.
- Локальный анализ включает промежуточные поручения и накопительную сводку; после остановки выполняется полный анализ доступной расшифровки. Фиксация задач не означает автоматическую отправку внешним системам.
- Обязательные уведомления о записи видны в интерфейсе; напоминания о сроках работают в открытом приложении. Email/Telegram, интеграция с СЭД и биометрические голосовые профили из дополнительных опций ТЗ не реализованы.
- Доступ по приглашению и персональному токену браузера; приглашение даёт доступ к содержимому встречи. Здесь нет корпоративного SSO/учётных записей. Утерянный токен организатора автоматически не восстанавливается.
- Старый сценарий загрузки файлов с pyannote остаётся в `backend/` и имеет отдельные инструкции/требования к HF-токену. Корневой стек обслуживает живые конференции; offline worker автоматически не запускается.

## Что проверено разработчиком

Автотесты проверяют права, приглашения, WebSocket-сигналинг двух участников, чат, формат/очередь аудио, повторную доставку между сеансами записи, привязку реплик к именам, редактирование задач и экспорт. В тестах вывода ИИ используются контролируемые ответы. Реальный разговор между двумя физическими ПК и скорость/качество ваших моделей нужно проверить по сценарию выше; локальная сборка сама по себе этого не доказывает.

## What Changed? перед следующей встречей

1. Завершите прошлый созвон кнопкой «Завершить для всех»: в этот момент сохраняется состояние поручений. Дождитесь итогового анализа.
2. Создайте новую встречу и выберите прошлую в поле «Сравнить с прошлым созвоном». Доступны ваши завершённые встречи из этого браузера.
3. Подтвердите, что участники новой встречи могут видеть сводку и цитаты. Можно добавить заметки о событиях после созвона: новые препятствия, принятые изменения и ответы на вопросы.
4. Откройте комнату: блок «Что изменилось?» готовится в фоне. До пяти пунктов, не более 60 слов основного текста, с раскрываемыми источниками. 30 секунд — время чтения, не обещание скорости локальной модели. Одна попытка обработки ограничена двумя минутами; при ошибке доступно повторение.
5. Проверьте источник каждого вывода. Поручение, которое уже было просрочено на прошлом созвоне, не выводится повторно как новая просрочка. Завершённые и отменённые поручения исключены.
6. После изменения поручений сводка становится устаревшей; при входе организатора в запланированную встречу успешная устаревшая сводка обновляется автоматически один раз. Кнопка «Обновить» позволяет повторить вручную. Новые заметки сохраняются кнопкой «Сохранить и обновить».

Сводка использует предыдущий созвон, текущие состояния его поручений и введённые организатором заметки. Она не наблюдает события в сторонних системах. Незакрытые вопросы извлекаются из явно отложенных вопросов прошлого разговора с учётом доступных новых сведений. Ошибки понимания модели возможны; цитаты дают возможность их проверить.

Для длинных разговоров контекст ограничен: сначала новые заметки и решения, затем изменения поручений и последние реплики. Если включены не все источники, интерфейс явно показывает частичный охват. Для старых завершённых встреч снимок поручений не создаётся задним числом. Доступ к связыванию встреч есть только у организатора обеих встреч; готовая сводка доступна всем участникам новой комнаты.
